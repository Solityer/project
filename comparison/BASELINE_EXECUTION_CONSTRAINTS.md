# 对比实验统一执行约束

> 适用范围：`comparison/baselines/ezkl/`、`comparison/baselines/zkdl/`、`comparison/baselines/zkGPT/` 三套独立对比实验。  
> 文件定位：本文件只描述长期有效的对比实验工作区边界、实现原则、主实验引用权限、方法学独立性、最小修改原则、验证边界和交付要求。  
> 本文件不记录某一轮具体修改步骤、临时错误、临时性能数字、日志位置、失败尝试或执行流水。  
> 本文件默认只读；只有项目负责人明确要求修改本文件时才允许修改。

---

## 0. 规范层级与解释原则

执行任一对比实验修改时，规范优先级固定为：

1. 项目负责人当前任务中明确、具体的要求；
2. 当前 baseline 目录中的 `GAT-ZKML-*.md` 协议笔记；
3. 本文件；
4. 当前 baseline 已有代码、原项目结构、原生 proof backend、原生优化与原有构建方式；
5. 主实验内容只作为只读参考和必要通用内容的复制来源。

其中：

- 协议笔记决定“证明什么、公开什么、隐藏什么、怎样证明以及什么情况下必须标记 unsupported”；
- 本文件决定“在哪里修改、允许借用什么、怎样保持 baseline 独立、做到什么程度即可停止”；
- 当前 baseline 已有实现应优先于重新实现；
- 主实验绝不是 baseline 的默认实现模板。

一般性任务目标，例如“让实验跑通”“完成实现”“修复问题”“做最小优化”，不自动构成突破本文件硬边界的授权。

只有项目负责人明确指出允许突破的具体规则、具体路径或具体行为时，才视为有效例外。

若协议笔记、当前 baseline 能力与本文件之间出现无法自行解决的真实冲突，必须停止冲突部分并报告，不得自行修改协议、主实验或本文件来消除冲突。

## 1. 项目目标与当前阶段

三个 baseline 的目标是形成三套：

- 彼此独立；
- 可单独构建；
- 可单独运行；
- 忠实实现各自协议笔记；
- 保留各自原生证明体系；
- 可用于与主实验进行方法学公平比较

的 GAT-ZKML 对比实验。

当前阶段不是对三个 baseline 开展系统级性能重构，而是：

> **以当前 baseline 为主体，完成协议要求下的最小可运行适配。**

因此当前工作的优先级是：

1. 忠实协议；
2. 真实证明与真实验证可以运行；
3. baseline 保持独立；
4. 修改范围尽可能小；
5. 保留 baseline 自己已有的原生优化；
6. 不主动把主实验的方法或优化迁移进来；
7. 在已经满足要求后及时停止修改。

“最小可运行修改”是指：

> 在不改变协议语义、不削弱证明、不改变方法学身份的前提下，优先复用当前 baseline 已有能力，只补充使其忠实实现协议笔记并能够独立运行所必需的最小实现。

“最小”描述的是修改范围，不描述证明强度、安全强度或验证强度。

## 2. 三个 baseline 的唯一可写目录

每次任务只能选择一个 baseline 作为当前目标。

| 当前目标 | 唯一允许写入的目录 | 对应协议笔记 |
|---|---|---|
| ezkl | `comparison/baselines/ezkl/**` | `comparison/baselines/ezkl/GAT-ZKML-ezkl.md` |
| zkDL | `comparison/baselines/zkdl/**` | `comparison/baselines/zkdl/GAT-ZKML-zkDL.md` |
| zkGPT | `comparison/baselines/zkGPT/**` | `comparison/baselines/zkGPT/GAT-ZKML-zkGPT.md` |

### 2.1 强制目录隔离

修改某个 baseline 时：

- 当前 baseline 目录是唯一允许写入的项目目录；
- 主实验全部内容只读；
- 另两个 baseline 目录只读；
- `comparison/BASELINE_EXECUTION_CONSTRAINTS.md` 只读；
- `comparison/results/`、`comparison/scripts/` 等当前 baseline 之外的 comparison 内容也只读，除非项目负责人针对某项任务明确授权。

禁止在当前 baseline 目录之外：

- 修改文件；
- 新建文件；
- 删除文件；
- 移动或重命名文件；
- 自动格式化后写回；
- 生成新的项目源码、配置或脚本；
- 修改构建入口；
- 为当前 baseline 增加主实验侧适配层；
- 为当前 baseline 改写另一个实验目录。

工具链自身使用的系统临时目录、编译缓存和包缓存不属于项目写入范围，但不得成为 baseline 的隐式运行依赖。

### 2.2 一次只修改一个 baseline

一次任务不得同时修改两个或三个 baseline。

例如修改 ezkl 时：

- 只允许改变 `comparison/baselines/ezkl/`；
- zkDL 保持不变；
- zkGPT 保持不变；
- 主实验保持不变。

其他 baseline 同理。

## 3. 主实验永久只读

修改任一 baseline 时，主实验内容永久视为只读参考。

允许：

- 阅读；
- 搜索；
- 分析；
- 对照；
- 查看主实验的 GAT 数值语义；
- 查看数据和模型输入方式；
- 查看配置和公共工具；
- 在确有必要时，把最小必要的通用内容复制到当前 baseline 内。

禁止：

- 修改主实验源码；
- 修改主实验头文件；
- 修改主实验配置；
- 修改主实验脚本；
- 修改主实验测试；
- 修改主实验构建文件；
- 为 baseline 给主实验增加接口；
- 为 baseline 给主实验增加条件分支；
- 为 baseline 创建主实验侧 adapter；
- 为 baseline 改写主实验已有执行路径。

唯一允许的借用模式是：

`主实验只读内容 -> 复制到当前 baseline -> 只修改 baseline 内副本`

绝不允许：

`修改主实验 -> 让 baseline 使用修改后的主实验`

## 4. 禁止对主实验形成隐式运行依赖

即使主实验文件没有被修改，也不得通过构建或运行时引用规避目录隔离。

当前 baseline 不得：

- 通过相对路径直接把主实验源码编译进来；
- 直接链接主实验为本项目生成的库或对象；
- 调用主实验可执行程序替代 baseline 的证明或验证；
- 依赖主实验运行后产生的中间证明结果、临时结果或缓存；
- 使用符号链接或其他路径映射，把主实验源文件伪装成 baseline 本地文件；
- 通过环境变量隐藏对主实验源码或构建产物的依赖；
- 依靠仓库根级构建逻辑注入主实验实现。

baseline 所需的源码、证明逻辑、配置、脚本和小型必要资源应位于自身目录中。

对于体积很大的公共只读数据集、模型输入或第三方资源，可以作为明确的外部输入使用，不要求机械复制；但不得要求这些外部输入先经过主实验程序修改或生成后才能运行 baseline。

## 5. 协议笔记是只读技术规范

当前 baseline 的 `GAT-ZKML-*.md` 是该实验的最高技术规范之一。

修改前必须完整阅读对应协议笔记。

协议笔记默认只读，不得为了迁就现有代码、减少工作量、提高性能或绕过 backend 限制而修改。

当实现与笔记冲突时：

1. 优先修正实现；
2. 如果 baseline 原生体系能够忠实补充，则做最小补充；
3. 如果确实无法忠实支持，则按笔记定义显式报告 unsupported；
4. 不得修改笔记把“不支持”重新定义为“支持”。

特别禁止为了跑通而改变：

- GAT 层数语义；
- attention head 语义；
- 隐藏层 concat；
- 输出 attention head；
- 输出 bias 位置；
- 最终多头平均；
- stable Softmax；
- 定点尺度链；
- `SignedRoundDiv`；
- rounding mode；
- 静态表语义；
- 图结构和 batch 语义；
- 公开/私有输入边界；
- 模型绑定方式；
- 最终公开输出；
- 协议笔记规定的安全或隐私边界。

## 6. Baseline-native first

每个需要的能力都必须按固定优先级处理。

### 6.1 当前 baseline 已有实现

如果当前 baseline 已经存在满足协议要求的实现：

- 直接复用；
- 不重写；
- 不从主实验复制替代版本；
- 不仅因为主实验更快、更成熟或更熟悉而替换。

### 6.2 已经可运行时直接停止扩展

如果当前 baseline 已经能够：

- 独立构建；
- 按协议完成真实 proof generation；
- 按协议完成真实 verification；
- 运行目标 GAT 实验路径；

则原则上不再修改生产实现。

此时应：

- 保留现有实现；
- 不从主实验复制任何新方法；
- 只做最低必要的运行确认；
- 报告当前实现已经满足要求。

不得仅因为“还能更快”“还能重构”“还能统一代码”而继续修改。

### 6.3 baseline 原生机制的最小扩展

如果缺少某个协议必需能力，但可以利用 baseline 自己的原生 proof system、backend 或原项目机制自然实现，则只做该最小扩展。

### 6.4 通用基础设施才允许参考主实验

只有在 baseline 自身确实缺少通用的 GAT/data/config/preprocessing/serialization 基础设施时，才允许参考并复制主实验中最小必要内容。

### 6.5 无法忠实支持时显式 unsupported

如果继续实现必须：

- 引入主实验专有证明方法；
- 改变 baseline 方法学身份；
- 弱化 relation；
- 弱化安全或隐私；
- 改变协议笔记定义的任务；

则不得继续导入该方法，应按协议笔记显式报告：

- `unsupported_exact_relation`；
- `unsupported_privacy_profile`；
- 或协议笔记定义的其他 unsupported 状态。

禁止 silent fallback。

## 7. 允许从主实验复制的内容

只有同时满足以下条件时才允许复制：

1. 当前 baseline 自身确实没有等价能力；
2. 协议实现确实需要；
3. 该内容不属于主实验专有证明方法或专有优化；
4. 复制后 baseline 仍然可以独立运行；
5. 只复制最小必要部分。

优先允许的类别包括：

- GAT 数据加载；
- 图数据解析；
- 模型权重读取；
- 与证明系统无关的 GAT 明文 forward/reference 逻辑；
- 必须一致的 graph preprocessing；
- 节点/边编号和 batch 预处理；
- 量化配置解析或生成；
- 静态表通用生成逻辑；
- 输入/输出序列化；
- 数据集配置；
- 模型结构配置；
- 实验输入准备；
- 与密码学后端无关的 utility；
- 为保持相同 GAT 数值语义所必需的通用参考实现。

复制时必须：

- 先确认 baseline 没有等价实现；
- 复制到当前 baseline 内；
- 只修改 baseline 内副本；
- 删除对主实验路径的运行依赖；
- 保留必要的许可证和版权信息；
- 最终说明复制了什么、从哪里复制、为什么必须复制。

## 8. 禁止迁移主实验专有证明方法和优化

主实验只用于提供只读参考，不用于把主实验的优化体系反向套到 baseline。

除非某项机制本来就是对应 baseline 原论文、原项目或原 backend 的自然组成部分，否则禁止从主实验迁入：

- 主实验专有 KZG 证明结构；
- 主实验 LogUp 组织；
- PSQ；
- CRPC；
- 主实验专用 commitment aggregation；
- 主实验专用 opening aggregation；
- 主实验 proof-local reblinding 体系；
- 主实验专用工作域布局；
- 主实验专用 Lagrange-SRS 热路径；
- 主实验专用 tensor-binding/route 结构；
- 主实验专用批量 MSM/NTT 组织；
- 主实验专用缓存体系；
- 主实验专用 CPU worker/NUMA 调度；
- 主实验专用 GPU kernel；
- 主实验专用 CUDA batching/streaming/buffer reuse；
- 主实验专用 CPU/GPU shape-aware routing；
- 主实验特有的 proof/constraint fusion；
- 为主实验专门设计的跨阶段性能重排；
- 其他明显改变 baseline 原算法、原证明体系或复杂度特征的主实验优化。

如果名称相同的技术本来就在 baseline 中存在，应继续使用 baseline 自己的实现，而不是复制主实验版本。

## 9. 不得人为削弱或人为做慢 baseline

方法学独立不意味着故意降低 baseline 性能。

必须保留并正常使用当前 baseline 已经具备的：

- 原生 proof backend；
- 原生 lookup；
- 原生 Sumcheck/GKR/Lasso/FAC4DNN 等机制；
- 原生 batching；
- 原生编译优化；
- 原生多线程；
- 原生 GPU 支持；
- 原生缓存；
- 原生 constraint fusion/circuit squeeze；
- 原项目默认且安全的有效性能路径。

不得为了“公平”而关闭 baseline 自己已有的原生正常优化。

也不得回退当前 baseline 已存在且正确有效的实现，除非它与协议笔记冲突或存在真实正确性/安全问题。

但是，当前阶段也不要求 Codex 主动寻找新的大规模性能优化；只要协议路径已经正确、真实并可运行，就应停止扩展。

## 10. 禁止伪运行、弱证明和安全降级

“可运行”必须指真实协议路径可以运行，不是表面返回成功。

正式实现禁止：

- mock proof；
- fake proof；
- fake verifier；
- verifier 无条件返回成功；
- 固定 Fiat–Shamir challenge；
- 把测试随机性直接当作正式 proving randomness；
- 只做明文重新计算而不执行密码学验证；
- 跳过 commitment；
- 跳过 opening/evaluation proof；
- 跳过 Sumcheck/GKR/Lasso/lookup 的必要检查；
- 只证明部分层；
- 只证明部分 attention head；
- 用 host-side assertion 代替证明约束；
- 利用已知 trapdoor 绕过正常证明流程；
- 为了运行或测速关闭零知识、binding 或必要验证后仍称为正式 profile；
- 把 unsupported profile 自动切换成更弱 profile；
- 复用本应 fresh 的 proof-specific randomness 或 proof；
- 用 replay proof 代替新 proof；
- 通过删除 verifier check 获得性能提升。

测试专用固定随机输入只能存在于明确的测试路径，不得进入正式 proving path。

任何能力、安全或隐私降级都必须显式失败、显式标记或显式报告。

## 11. 三个 baseline 的方法学身份

### 11.1 ezkl

`comparison/baselines/ezkl/` 必须继续以 ezkl/Halo2 原生体系为主体。

如果 ezkl 自身 gate、lookup、Halo2 argument 和现有编译路径能够完成某项关系，应直接使用。

不得为了实现 GAT 而把主实验专有证明体系迁入。

### 11.2 zkDL

`comparison/baselines/zkdl/` 必须继续以 zkDL-style 的 MLE、Sumcheck、Pedersen/Hyrax、FAC4DNN 和其原生 evaluation 体系为主体。

不得用主实验证明框架替代这些机制。

### 11.3 zkGPT

`comparison/baselines/zkGPT/` 必须继续以 zkGPT 原生 GKR、Lasso、Hyrax、矩阵乘 Sumcheck、advice、constraint fusion/circuit squeeze 等机制为主体。

不得以主实验证明框架替代这些机制。

具体安全边界、adaptation、repair 和 unsupported 条件，以各自 `GAT-ZKML-*.md` 为准。

## 12. 代码修改必须最小、局部

除协议实现确有必要外，不进行与当前任务无关的工程重构。

默认禁止：

- 大规模目录重组；
- 全项目重命名；
- 全文件格式化；
- 大面积无关注释更新；
- 顺手清理无关技术债；
- 替换整个构建系统；
- 大范围升级依赖；
- 更换密码学库；
- 更换曲线或有限域；
- 重写已经可用的模块；
- 为统一三个 baseline 而新建公共 framework；
- 为代码风格一致而让三个 baseline 共享新的实现层；
- 仅为了追求进一步性能而开展与“跑通协议”无关的大范围优化。

依赖和工具链调整必须满足：

- 只发生在当前 baseline 内；
- 只处理运行当前协议所必需的问题；
- 不升级无关依赖；
- 不因为环境问题而改变协议；
- 不因为“新版更方便”而整体替换当前 baseline 框架。

如果外部依赖、编译器、CUDA 或第三方组件缺失，应作为环境问题报告；不得通过弱化协议或假实现绕过。

## 13. 独立构建与独立运行

每个 baseline 最终都必须能够作为自己的实验工程运行。

至少满足：

- 有自己的构建配置；
- 有自己的源码和 proof implementation；
- 有自己的必要配置；
- 有自己的运行入口或脚本；
- 有自己的输出位置；
- 不要求修改主实验；
- 不要求构建主实验后才能证明或验证；
- 不要求先运行另一个 baseline；
- 不把主实验程序当作 proving/verifying 子进程。

允许依赖标准系统工具链、明确声明的第三方库以及显式传入的只读数据/模型输入。

“独立运行”不要求把操作系统、CUDA、Rust/C++ 工具链或巨型公共数据复制进 baseline，但要求 baseline 自己的代码和证明路径不存在对其他实验实现的隐式依赖。

---

## 14. 公平比较与实验语义

不得通过改变任务本身来让某个 baseline 更容易运行或更快。

除协议笔记明确允许外，不得为某个 baseline 单独改变：

- 数据集；
- 样本选择规则；
- 图拓扑；
- 节点/边排序语义；
- 模型结构；
- 层数；
- attention head 数；
- hidden dimension；
- 类别数；
- 模型权重；
- 量化尺度；
- rounding mode；
- static-table 语义；
- public/private policy；
- 最终 logits 定义；
- 目标安全或隐私 profile。

如果某个 baseline 不能忠实支持目标 relation，应报告 unsupported，而不是修改比较任务。

不得把主实验的证明结果、运行结果、耗时或成功标志当作 baseline 自己的结果。

## 15. CPU / GPU 边界

baseline 如果原生支持 GPU，可以继续使用原生 GPU 路径。

如果 baseline 当前只有 CPU 路径，则先保持 CPU 路径；当前阶段不要求仅为了与主实验一致而额外移植 GPU 实现。

禁止仅为了让 baseline 更快而复制主实验的：

- GPU kernel；
- CUDA pipeline；
- GPU MSM/NTT；
- 主实验设备缓存；
- 主实验专用调度体系。

如果某项新增 GPU 能力只能通过主实验专有优化完成，则默认不新增，除非项目负责人明确授权。

任何 GPU 运行都必须来自真实 GPU 执行；发生 CPU fallback 时应如实说明。

## 16. 计时与结果真实性

当前阶段的首要任务是把 baseline 的真实协议路径跑通，而不是围绕计时做额外性能工程。

如果进行对比运行：

- 保持当前 baseline 自己已有且合理的计时边界；
- 不为了得到更好的数字移动工作；
- 不把原本属于 proving/verifying 的工作偷偷移到不计时阶段；
- 不通过复用 fresh-proof 必需工作制造更快结果；
- setup/preprocessing、proof generation、verification 和 proof size 应按各自实际边界区分；
- 不手工改写实验输出制造结果；
- 不用 toy/smoke 结果冒充正式数据集结果；
- 不把更弱 profile 的结果标记成严格 profile。

如果 baseline 自然计时边界与其他 backend 不完全相同，应如实保留，不为了表面统一而改变其原生执行结构。

正式大规模性能实验和最终对比结果由项目负责人决定何时执行。

## 17. 测试与验证边界

代码修改完成后必须进行测试，但测试目标只有一个：

> **确认当前修改后的 baseline 能够真实、正确地跑通目标实验路径。**

测试不是独立开发目标，也不是为了穷举所有可能情况。

### 17.1 最低必要验证

原则上完成以下内容即可：

1. 当前 baseline 能正常构建；
2. 使用一个低成本、能够触发当前 baseline 真实目标证明与验证路径的实验实例运行目标路径；
3. 真实 proof generation 成功；
4. 真实 verification 成功；
5. 关键输出与协议要求一致；
6. 只有当正常端到端运行无法判断本轮问题是否已解决，或者项目负责人明确要求时，才补充一个与当前问题直接相关的针对性测试；不得默认新增失败用例或扩展测试范围。

不要求每次修改后执行大量单元测试、完整回归、长时间 benchmark 或全面 profiling。

### 17.2 不允许无限制反复测试

必须遵守：

- 不以“多测几次更放心”为理由重复执行已经成功且没有新信息的同一测试；
- 不为了刷新结果反复运行；
- 不形成“改一个函数 -> 大量测试 -> 再改一点 -> 再大量测试”的循环；
- 多个相关修改应集中完成后统一做一次最低必要验证；
- 测试失败时先定位并完成实质修改，再重新运行受影响测试；
- 如果失败原因已经明确是环境问题，不反复执行相同失败命令；
- 已有结果足以确认实验能跑通时立即停止继续验证；
- 不为了验证 test/helper 本身再建立新的测试链；
- 不主动增加 benchmark、profiler 或额外测试工具，除非现有方式无法判断实验是否能跑通。

### 17.3 默认不运行全量实验

开发阶段默认不执行：

- 五个正式数据集的完整实验矩阵；
- CPU/GPU 全组合完整实验；
- 长时间完整 benchmark；
- 大规模 profiling；
- 重新训练模型；
- 大规模正式参数生成；
- 其他高资源、长时间操作。

除非项目负责人明确要求，否则开发执行方只需要把代码、配置、脚本和入口准备到可直接运行状态，并用一个低成本、能够触发当前 baseline 真实目标证明与验证路径的实验实例确认可以跑通。

### 17.4 测试结束条件

满足以下条件时应停止测试：

- 构建成功；
- 一个低成本目标实验实例能够端到端完成，并实际触发当前 baseline 的目标证明与验证路径；
- proof generation 成功；
- verification 成功；
- 没有发现与本轮修改直接相关的新错误；
- 当前任务没有明确要求额外性能实验。

达到上述条件后，不再继续扩展测试范围。

## 18. 长时间和高资源操作

参考主实验 `PROJECT_CONTEXT_AND_EXECUTION_CONSTRAINTS.md` 的长期执行原则：长时间、高资源、最终正式数据集实验不应在普通代码修改过程中反复执行；测试、benchmark 和 profiling 只服务于判断实现是否正确和是否能够运行，不形成递归验证链；正式完整实验应在代码和实验准备完成后再执行。

因此修改 baseline 时：

- 先完成所有不依赖长时间操作即可完成的代码工作；
- 先完成配置、参数、脚本、容量检查和运行入口；
- 用一个低成本、能够触发当前 baseline 真实目标证明与验证路径的实验实例确认路径可以运行；
- 只有项目负责人明确要求时，才执行正式长时间实验。

不得因为后续可能需要大规模实验，就提前停止当前仍能完成的代码工作。

也不得为了“确认得更充分”在开发阶段反复执行长时间实验。

## 19. 修改范围检查

完成代码修改后，在测试前先检查本轮实际触碰的项目文件。

必须确认：

- 所有新增、修改、删除都位于当前 baseline 目录；
- 主实验没有被本轮修改；
- 另两个 baseline 没有被本轮修改；
- 本执行约束文件没有被本轮修改；
- 当前 baseline 协议笔记没有被为了迁就实现而修改。

如果发现本轮操作越过当前 baseline 可写目录，应先撤销**本轮自己造成的越界变化**，再继续。

不得修改、覆盖或清理项目负责人已有的其他工作内容。

目录隔离是硬门，不是建议。

## 20. 从主实验复制内容时的说明要求

如果本轮从主实验复制了代码、配置、脚本或逻辑，最终报告必须逐项说明：

- `SOURCE`：主实验原路径；
- `DESTINATION`：当前 baseline 内目标路径；
- `REASON`：为什么 baseline 自身没有等价能力、为什么必须复制；
- `TYPE`：data / config / preprocessing / forward-reference / serialization / utility / other；

正常情况下，复制内容不应包含主实验专有证明系统逻辑。

如果拟复制内容可能涉及主实验专有证明方法或专有性能优化，应停止复制并等待项目负责人判断。

不得通过路径映射、链接或其他方式规避上述说明要求。

## 21. 依赖、第三方组件与版本边界

当前 baseline 已有框架、第三方组件和依赖关系默认保持。

除非运行协议确实需要，否则不得：

- 整体替换 baseline 框架；
- 切换到另一个上游实现；
- 大范围更新第三方依赖；
- 更换密码学库；
- 更换曲线、有限域或 proof backend；
- 为了方便开发而改用与当前 baseline 方法学不同的实现。

如果某项依赖调整确实是运行所必需：

- 只能在当前 baseline 内处理；
- 只改必要部分；
- 不扩散到主实验或另一个 baseline；
- 最终说明为什么必须调整以及是否影响证明、安全、隐私或性能口径。

## 22. 已有结果和实验材料保护

普通实现修改任务不应顺手清理、覆盖或重组已有实验结果。

必须遵守：

- 不删除已有正式结果；
- 不覆盖已有结果文件来制造新的“当前结果”；
- 不删除旧结果仅为了保留更好的数字；
- 开发测试输出优先放在当前 baseline 自己的临时或运行目录；
- 当前 baseline 之外的结果目录默认只读；
- 是否汇总到全局 comparison 结果由项目负责人另行决定。

临时测试产物如果没有长期价值，可以在当前 baseline 内完成任务后清理；不得因此清理主实验或其他 baseline 的材料。

## 23. Fail-closed 与停止条件

出现以下情况时必须停止对应实现并报告：

- 需要修改主实验才能继续；
- 需要修改另一个 baseline 才能继续；
- 需要修改本执行约束文件才能继续；
- 需要修改协议笔记才能让现有实现“匹配”；
- 只能通过弱化 relation 才能运行；
- 只能通过删除密码学检查才可运行；
- 只能通过主实验专有 proof technique 才能实现；
- 目标 privacy/security profile 无法由当前 backend 支持；
- 环境或依赖缺失且无法在当前 baseline 内合理解决；
- 发现真实 soundness/privacy/correctness 问题，需要先确定修复策略；
- 无法判断某项拟复制内容究竟属于通用基础设施还是主实验专有方法；
- 实验结果与协议预期严重矛盾，需要先定位；
- 当前 baseline 已经合规可运行，不再需要额外修改。

报告问题优先于制造一个表面可运行但不合规的结果。

## 24. 修改前的执行流程

每次修改某个 baseline 前，按以下顺序：

1. 明确当前目标 baseline 和唯一可写目录；
2. 完整阅读本文件；
3. 完整阅读当前 baseline 的 `GAT-ZKML-*.md`；
4. 阅读当前 baseline 的 README、构建配置、源码、tests、scripts、configs；
5. 先判断当前代码是否已经能够直接运行协议要求的实验；
6. 如果已经可以运行，原则上不修改生产实现，只做最低必要确认；
7. 如果不能运行，列出真正缺失的最小能力；
8. 对每个缺失能力优先寻找 baseline-native 实现路径；
9. 只有缺失项属于通用基础设施时，才查看主实验对应内容；
10. 在复制前确认不会引入主实验专有证明方法或优化；
11. 所有写操作保持在当前 baseline 内。

禁止一开始就照主实验结构重构 baseline。

### 24.1 协议、实际代码与文字说明的可信等级

判断当前 baseline 的真实实现状态时，统一采用以下优先级：

1. 当前 baseline 的 `GAT-ZKML-*.md` 是协议与安全边界的最高规范；
2. 当前实际生产代码路径、构建行为和真实运行行为用于判断“现在到底实现了什么、能否运行”；
3. README、源码注释、历史说明、旧脚本描述和测试文字只作为辅助理解材料。

因此：

- 不得仅凭 README、注释或历史说明认定某项能力已经实现或尚未实现；
- 如果文字说明与当前实际代码行为不一致，应以协议笔记和实际代码/运行行为为准进行判断；
- 不得为了匹配过时注释或旧 README 而修改本来正确且符合协议的实现；
- 不得仅因为历史文字提到某项功能、优化或 TODO，就自动扩大本轮修改范围；
- 只有实际代码路径和运行行为表明存在与当前任务直接相关的缺口时，才进行必要修改。

## 25. 修改后的执行流程

完成修改后，按以下顺序：

1. 检查本轮修改范围是否全部位于当前 baseline；
2. 确认主实验、另两个 baseline、本文件和协议笔记未被本轮违规修改；
3. 构建当前 baseline；
4. 运行一个低成本、能够触发当前 baseline 真实目标证明与验证路径的实验实例；
5. 确认真实 proof generation 成功；
6. 确认真实 verification 成功；
7. 只有当正常端到端运行无法判断本轮问题是否已解决，或者项目负责人明确要求时，才执行一个直接相关的针对性测试；不得默认增加失败用例；
8. 一旦上述验证足以说明实验可以跑通，立即停止继续测试；
9. 不运行全量正式实验，除非项目负责人明确要求；
10. 汇总本轮实际修改、必要依赖调整、主实验复制内容和 unsupported 状态；
11. 输出简洁、可审计的完成报告。

不能只以“编译成功”作为完成标准，也不能把“测试越多越好”作为完成标准。

## 27. 最终验收门

一个 baseline 只有同时满足以下条件，才能视为本轮修改完成。

### Gate A — Workspace isolation

本轮所有项目修改只发生在当前 baseline 目录。

### Gate B — Main experiment integrity

主实验没有被本轮修改，也没有为了 baseline 增加 adapter 或兼容路径。

### Gate C — Protocol fidelity

没有改变或弱化 `GAT-ZKML-*.md` 定义的 relation、安全和隐私边界。

### Gate D — Methodological independence

没有把主实验专有证明方法或专有性能优化迁入 baseline。

### Gate E — Baseline-native preservation

优先使用并保留 baseline 自己已有的证明体系和有效原生优化。

### Gate F — Real cryptographic execution

关键证明与验证路径真实执行，不是 mock、fake 或 host-only 检查。

### Gate G — Independent build/run

baseline 不依赖被修改的主实验或另一个 baseline 才能运行。

### Gate H — Minimal validation

完成足以确认目标实验端到端可以跑通的最低必要验证，没有无限制重复测试。

### Gate I — Honest status

复制内容、unsupported 能力、环境限制和实际验证结果均已如实报告。

任何 Gate 未通过，都不能把该 baseline 标记为完成。

## 28. 核心判断树

```text
当前 baseline 已经实现所需能力？
    是
      -> 直接复用。
      -> 不用主实验替换。

    否
      -> 能否用 baseline 自己的原生 proof/backend 机制做最小扩展？

         能
           -> 只在当前 baseline 内做最小扩展。

         不能
           -> 缺失的是否只是通用 GAT / data / config /
              preprocessing / serialization 基础设施？

              是
                -> 从只读主实验复制最小必要内容到当前 baseline。
                -> 只修改 baseline 内副本。

              否
                -> 是否必须引入主实验专有证明方法、
                   安全捷径或专有性能优化？

                   是
                     -> 不导入。
                     -> 按协议笔记报告 unsupported。

                   不确定
                     -> 停止并由项目负责人判断。
```

另外：

```text
当前 baseline 已经能独立完成真实 proof + real verification + 目标实验？
    是
      -> 不继续优化。
      -> 不复制主实验新方法。
      -> 做一次最低必要确认后停止。
```

## 29. 最终不可突破原则

1. **主实验永远不可修改，只允许查看和必要复制。**
2. **修改哪个 baseline，所有项目写操作只能发生在该 baseline 目录。**
3. **三个 baseline 必须保持彼此独立。**
4. **协议笔记不可为了代码而修改。**
5. **当前 baseline 已经能直接实现的能力，不得用主实验替换。**
6. **当前 baseline 已经可以忠实跑通时，不再为了进一步优化而继续修改。**
7. **优先 baseline-native；主实验复制只用于真正缺失的通用基础设施。**
8. **不得把主实验专有证明方法和优化体系反向移植到 baseline。**
9. **不得人为关闭 baseline 自己已有的正常原生优化。**
10. **最小修改不等于弱证明，不允许 mock、fake、跳过或静默降级。**
11. **无法忠实支持时明确 unsupported，而不是改变任务或伪装支持。**
12. **开发测试只做到足以确认实验真实跑通，不进行无限制反复测试。**
13. **默认不运行全量数据集、长时间 benchmark、大规模 profiling 或其他重型操作。**
14. **一次相关修改形成后统一做最低必要验证，不对每个小改动反复大测。**
15. **达到“构建成功 + 低成本目标实验实例端到端完成 + proof 成功 + verification 成功”后应停止测试。**
16. **所有主实验复制必须最小、必要、可说明来源与用途。**
17. **正确性、协议忠实性、安全性和方法学独立性优先于便利、代码复用和性能。**
18. **最终完整实验、正式性能结果和是否继续优化，由项目负责人决定。**
